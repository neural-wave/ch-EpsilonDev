# Model history

Every change to the LLM and to what it reads, oldest first: what changed, why, what was measured, and what was decided. For teammates, for the jury, and for whoever writes the final report. Whoever changes anything listed here adds an entry the same day ([section 7](#7-how-to-add-an-entry)).

## 1. Scope, sources and metrics

**What counts as a model change.** The model and how it is served (build, quantization, server settings); how it decodes (thinking, temperature); its answer caps; its prompts; the context it reads with each request (examples, schema cards, code candidates); and what it reads on a retry (the judge's and the guard's feedback, the retry budget). The judge and the guard are code. Their changes are listed only where they change what the model reads or which of its answers is kept; the details are in [FAILURE_ANALYSIS.md](FAILURE_ANALYSIS.md) and [GUARD.md](GUARD.md). Connection settings (server address, TLS, tokens) are not listed.

**Where the raw numbers live.**
- `eval/reports/` on the run machine, git-ignored: one JSON report per eval run, recording the models, prompt versions, answer caps and context it ran with. `intent-*` is the intent agent alone, `query-*` the query agent against reference SPARQL, `pipeline-*` the whole pipeline, `perf-*` the timing on 100,000 patients. The three pipeline reports made before 17 October 01:00 have no prefix.
- `eval/reports/notes.json`: the label of each run, written by `eval/run_all.py --label` or on the runs page of the agents console.
- [PERFORMANCE.md](PERFORMANCE.md): the scoreboard of every run. This file names the report behind each number.

**Metrics.**
- **Right numbers**: the generated query, executed on the dev database (2,000 patients), returns the reference SPARQL's result, either `exact` or `exact_numbers` (the same numbers with other labels, rounding or layout). `exact_numbers` exists since 17 Oct 16:18; before, only `exact` counted.
- **Queries that run**: generated queries that Virtuoso executes without an error.
- **First try**: first answers the judge accepts. The judge became stricter at 17 Oct 16:18, so later rates do not compare with earlier ones.
- **Verdicts**: `is_compliant` against the label on 198 questions (149 dev, 49 holdout), with the **leaks** (forbidden requests marked compliant) and the **allowed requests blocked**.
- **Intent eval**: the intent agent alone on the same 198 questions: forbidden requests detected, false alarms on allowed ones, and the right flag (a question labeled with a rule raises that rule's flag).
- **Time and tokens**: p50 / p95 per request at concurrency 4; tokens per request, or the median query-agent tokens per question.

**Question sets.** "198" is the verdict set. The query eval had 47 questions until 17 Oct 13:48 (11 official, 21 dev, 15 holdout) and has 87 since (11 official, 45 dev, 31 holdout). The first intent set had 73 questions, all of them studied.

**Dev and blind holdout.** Dev questions may be studied one by one. Holdout questions are a blind exam: nobody reads them, nothing is tuned on them, and this file gives only their aggregate numbers. A change is kept only if the holdout does not get worse beyond the noise.

**Noise.** Identical runs differ by about one or two questions. vLLM decodes at temperature 0, but batching makes the answers non-deterministic: two identical Qwen3.5-9B runs of the 198 set (`pipeline-20261017-132835.json`, `pipeline-20261017-142628.json`) flipped 9 verdicts and differed by 2 of the 49 holdout questions. Qwen3.6-27B gave 19 of 31 right numbers on the holdout in three runs, and in a fourth after the age fix (21:50), with the same right or wrong outcome on every holdout question each time.

**Contamination.** Since 17 Oct 20:08 (the first run with `CONTEXT_DEV_REFERENCES=true`, `query-20261017-200810.json`; the default since 20:20) the 45 dev reference queries are retrieval examples, so a dev question sees its neighbours' references. From then on dev numbers are contaminated and only the holdout counts. The official questions never retrieve their own example, but they are dev questions: they were studied one by one, and fixes and the 16:18 team examples were designed from their failures. So from 20:08 only the holdout is a clean measure; the 21:40 run (`query-20261017-214008.json`) also added variants of the official questions to the bank.

## 4. Details

### 4.1 The first model: Qwen3.5-9B (17 Oct, 00:18)

The rules set the field. Every model in the system must have an open-source licence. The organizers encourage Apertus. Smaller models score better on a minor criterion. The design of 16 October named two kinds of candidates, Apertus 8B Instruct and an Apache-2.0 instruct or coder model of 7–14B parameters, and one rule: pick the smallest model that meets the test bench targets. Llama-family models were excluded because their licence is not open source in the strict sense.

`Qwen/Qwen3.5-9B` fits that description: Apache-2.0, not gated, 9.7B parameters, about 19 GB in bf16, which leaves room for the KV cache on a 32 GB GPU. It was the first model connected; no other model was measured before it. Its first two runs on the 31 shared questions gave 87.1% and 90.3% correct verdicts (the stub: 87.1%), with no forbidden request marked compliant, at about 3,000 tokens per request and a p50 of 2.8–3.2 s.

Both agents use it, with different prompts. One served model means one GPU and one server. From the first settings (16 Oct 23:13) the intent agent could take its own model (`LLM_INTENT_MODEL`); since 17 Oct 01:18 it can also have its own server, key, extra fields and answer cap. No measured run has used two models. Apertus for the intent agent was planned and never run ([section 6](#6-pending-experiments)).

It stayed the model until 21:00. The morning test of two code models did not beat it (section 4.8), and the day's gains until 20:20 came from prompts, context and the judge.

### 4.2 Decoding: temperature 0, thinking off

**Temperature 0.** Every call is greedy, so a run can be repeated and compared with the run before. It is not fully repeatable: vLLM batches requests, and two identical Qwen3.5-9B runs of the 198 set flipped 9 verdicts. That is why a change worth one or two questions needs a second run. Qwen3.6-27B was steadier: 19 of 31 on the holdout in three runs, and in a fourth after the age fix. Since the thinking test (before 21:26; committed at 21:56) the extra request fields may set temperature, top_p and top_k; only the thinking experiment used that. Best-of-N sends its own `QUERY_CANDIDATE_TEMPERATURE` (0.7).

**Thinking off.** Qwen3.5 and Qwen3.6 reason before they answer unless told not to. In the first test, on 17 October at 00:15, the model spent its whole 600-token budget reasoning and returned nothing after 7 s. With thinking off it answered in 1.2 s with 47 tokens. Every call has sent `enable_thinking: false` since.

**Thinking re-tested with Qwen3.6-27B (21:26–21:32).** The question was whether reasoning helps on long, multi-part questions when it has room. A fair test follows Qwen's model card, which warns that thinking mode repeats itself endlessly under greedy decoding: temperature 0.6, top_p 0.95, top_k 20, an 8,000-token cap, 300 s per call and 400 s per request, for the query agent only. The intent agent kept thinking off.

Time per request is a main criterion, and one more question in one sampled run does not pay for ten times the median time. Thinking stays off. The thinking runs used concurrency 5 (holdout) and 3 (official) instead of 4, so their latencies compare only roughly; the gap is far larger than that difference.

### 4.3 Answer caps

- **Intent agent: 200 tokens.** Its answer is a short JSON (five flags, a reason, a rephrase). No intent report has a cut-off answer.
- **Query agent: 900, then 1,500 tokens.** In the merged system's 198 run, 7 first answers and 3 retries hit 900, and 2 allowed requests ended blocked because their query was cut off (`pipeline-20261017-045145.json`). At 13:05 the cap went to 1,500 together with query prompt v4. Cut-off answers went 10 → 4 in that run (`pipeline-20261017-132835.json`), but the identical noise-check run logged 11 (9 first answers, 2 retries; `pipeline-20261017-142628.json`), so the cap's effect on cut-offs is within the run-to-run spread. A cap costs nothing unless an answer needs it. It was not raised further; the team's reading, not measured, is that the answers still cut off at 1,500 need a shorter query shape, not more room. A rejected answer that was cut off gets a retry that asks for a shorter query. With Qwen3.6-27B, 4 first answers of the 198 set hit the cap (`pipeline-20261017-211358.json`).
- **8,000 tokens** only for the thinking test.

**Decision (21:00).** Qwen3.6-27B for both agents, set on the GPU instance and in the run machine's `.env` (`LLM_QUERY_MODEL`). No code default changed. Qwen3.8-27B was not adopted: fewer right numbers and more Virtuoso errors than Qwen3.6-27B at the same first-try rate, although it is newer. The gain was not small (holdout 10 → 19 of 31), so the GPU stayed.

**Why the bigger model helps now** (interpretation, not measured directly):
- The 27B writes queries that pass the judge on the first try far more often (45% → 83% on the 87 questions), so it needs fewer retries. That is also why its median time and tokens on the query eval went down.
- The morning test measured exact results on 47 questions, before the judge's repairs, the richer context and the dev references existed. Every model then scored 0 of 15 exact on the holdout and 2–3 of 47 overall, so that test had little room to separate them.
- Qwen3.6-27B is a newer generation than Qwen3-Coder-30B-A3B, and dense: all 27.8B parameters work on every token, against about 3B active in the 30B mixture of experts.

**Trade-offs.**
- Smaller models are preferred (a minor criterion). The 27B has about three times the 9B's parameters. In 4 bits its weights take 19.6 GB, about what the 9B took in bf16 (about 19 GB).
- A jury that serves the model itself needs a GPU with 32 GB or more (24 GB was enough for the 9B): `vllm serve cyankiwi/Qwen3.6-27B-AWQ-INT4 --max-model-len 32000 --max-num-seqs 8`.
- Time per request is a main criterion. Each call is slower (the median query-agent call in the 198 run went 3.9 → 5.2 s), but about half as many requests need a retry. On the 198 set the median request went 4.0 → 5.3 s and the p95 24.2 → 17.9 s; on the 87 compliant questions the median went 8.7 → 7.2 s.

**Query time on 100,000 patients** (21:55, `perf-20261017-215503.json`: the 80 queries of `query-20261017-210737.json` that ran on dev, plain runs, 30 s client deadline): 58 of 80 pairs complete on both sides, median 0.3 s against 0.5 s for the references (median ratio 0.9); 10 generated and 19 reference queries pass 30 s; 6 generated queries are slower than their reference (Qwen3.5-9B: 9 of 74, `perf-20261017-211133.json`). **Not yet measured with Qwen3.6-27B:** the 31-question `--execute` run and the load test ([section 6](#6-pending-experiments)).

**Tested on the 27B and rejected (21:26–21:50):** thinking mode (section 4.2), 41 more examples (section 4.6) and best of 3 (timeline, 21:50: 18 of 31 against 19).

## 7. How to add an entry

1. **Change one thing**: the model, a decoding setting, a cap, a prompt version, a context size or a retry rule. Add a prompt as a new version next to the old ones; never edit an old version. Keep a rejected option behind its flag or version, off by default, so its reports stay reproducible.
2. **Label the run.** `python eval/run_all.py --label "<what changed>"` runs the intent, query and pipeline evals (and the timing on 100,000 patients) and saves the label in `eval/reports/notes.json` for each report. Add `--skip-intent` when the change cannot reach the intent agent and `--skip-perf` when the perf database is busy. A run made by hand gets its note on the runs page of the agents console (`/agents/runs`).
3. **Run the holdout twice when the change is noisy**: when the expected effect is one or two questions, when the change samples (temperature above 0, thinking, best-of-N), or when the first run disagrees with earlier ones. `python eval/run_query_eval.py --split holdout --concurrency 4` runs the 31 holdout questions alone. Compare holdout with holdout: dev is contaminated while `CONTEXT_DEV_REFERENCES=true`, and the official examples are contaminated by any example written from them.
4. **Record the report names and the numbers**: one timeline row here (When, Change, Why, Measurement with the report file names and the run it is compared with, Decision), the matching row in [PERFORMANCE.md](PERFORMANCE.md), and a part of section 4 when the change is a model, a prompt version or the context. Holdout numbers are counts or rates only.
5. **Write the decision and the reason the same day**, rejected changes included. A decision says adopted, rejected or pending, and why in one sentence. An experiment that is not measured yet goes in section 6.
6. **For a model change**, also record the repository name, the quantization, the weights in GPU memory, the KV cache size and the vLLM settings, and update section 2, README §8, the jury setup in README §6 and [LLM_AGENTS.md](LLM_AGENTS.md) §3. Re-test the model when the pipeline changes a lot: on 17 October a bigger model did not help in the morning and did in the evening, after the pipeline had changed.
7. **Never write** host names, addresses, ports or tokens; terminology labels or code identifiers; or anything about individual holdout questions.

A timeline row:

```
| 18 Oct 09:00 | **What changed**, with the setting or version | The failure or number that motivated it | The numbers (`<report>.json`) against the run before (`<report>.json`) | Adopted, rejected or pending, and why |
```
