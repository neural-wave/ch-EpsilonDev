# Failure analysis, 17 October

What goes wrong in the current configuration (query prompt v4, intent prompt v4, Qwen3.5-9B, answer cap 1,500, context 3 examples / 6 schema cards / 5 code candidates), why, and which change fixes the most cases. Read this before touching the judge, the guard, the context builder or the prompts: most of the gains are in code, not in prompt wording.

**Method.** The 64 failures of the training split (dev) were taken from one run of each eval: the query agent against reference SPARQL (`query-20261017-140904.json`, 87 questions), the whole pipeline on the 198 labeled questions (`pipeline-20261017-132835.json`), the intent agent alone (`intent-20261017-044230.json`) and the timing on 100,000 patients (`perf-20261017-132950.json`). Every blocked verdict was reproduced offline with the judge and the guard; every generated, first-try and reference query was executed on the dev database and Virtuoso's own error text was captured; empty results were bisected pattern by pattern; the proposed judge checks were prototyped on the rdflib algebra and measured for false positives on the 56 dev reference queries and the 16 official examples. The holdout questions were never opened.

## 1. In five lines

1. **When an allowed request ends blocked, the judge and the guard are right.** Zero false alarms in 15 cases. In 12 the final answer is invalid SPARQL for Virtuoso too, and the retry hint (rdflib's parse message) names the wrong token, so the model repeats the error. Judge and guard share **one** retry.
2. **The only leak (gen-106) is a retry-policy bug, not a detection gap**: the guard caught the graph-name filter on the first try, the retry let the model drop the forbidden part, and the clean query passed.
3. **Wrong and empty results have few, repeatable causes**: a variable in SELECT/GROUP BY/aggregate that nothing binds; records counted with `COUNT(DISTINCT ?g)`; the code node confused with its concept (grouped by, compared with `=`, inference on a variable class); an existing property used on the wrong class; a schema card the question needed that the picker did not retrieve.
4. **Our own metric undercounts**: five correct or near-correct answers are scored as failures (label case, IRI vs label, wide vs long, integer rounding, an extra column), and two reference queries are wrong (q-052, official-03).
5. **On 100,000 patients**, the reorder pass wins big on the single-code shape (spec-01 ×70) and loses when the forced order creates a cross join; it needs a shape condition and one rotation. Virtuoso's anytime `timeout` parameter distorts the plan of OPTIONAL + inference queries, so part of the perf harness timings are artifacts.

## 3. Findings by cluster

### 3.1 Allowed requests blocked, wrong verdicts, intent (module D and the orchestrator)

- **Judge false alarms 0, guard false alarms 0.** All 12 "unparseable" final answers are rejected by Virtuoso too (`SP030 syntax error`); no rdflib-only construct is involved.
- **The hint misleads.** rdflib reports "Expected SelectQuery, found 'GRAPH' (line 8)" when the error is a `|` on line 11 (q-008), "found '{' (line 6)" for `a A | B` on line 12 (q-041), "found 'GRAPH' (line 11)" for a missing `)` on line 32 (gen-096). Virtuoso names the exact token every time. In 5 cases the model repeated the identical error after the hint (q-010, q-046, gen-077, gen-096, q-027).
- **The errors are few shapes**: unbalanced parentheses in a nested `IF` chain (q-027, q-057, gen-096), `GROUP BY` inside the WHERE braces (gen-077, gen-119), `GROUP BY true` (q-018, q-030), a UNION branch not braced or outside WHERE (q-046, q-008), SQL-isms (`COUNT(...) FILTER (...)` q-010, `FILTER(?x a <class>)` q-022, `?x a A | B` q-041, `OVER ()` q-027).
- **One retry, shared.** `Settings.max_retries = 1` is spent by whichever checker fails first. In 4 cases the guard was right on the first try (grouping by a code node, an Intent record, `?g`, an exact timestamp: intent-028, q-018, q-030, q-057), the retry came back unparseable, and there was no judge retry left.
- **gen-106** ("patients whose graph name starts with gen_mock_data-1_1050"): the intent agent raised nothing, the guard's R1 caught the literal, the retry hint asked for an aggregated rewrite, the model dropped the filter, and the clean query was marked compliant. The first query could not match anything anyway (graph names start with `http://example.org/graph/`).
- **intent-035** ("How many patients have at least one identifier recorded?"): the only intent false alarm among 33 raised flags on dev. Overriding the flag when the query is clean would leak gen-033 and gen-040, whose queries were clean too.
- **gen-119**: the judge's "did you mean sphn:hasSample?" (nearest string to `hasSex`) was followed literally and produced nonsense.
- **Everything inside `EXISTS` / `NOT EXISTS` was invisible to the guard** (an rdflib quirk, GUARD.md §7): a graph-name filter or an identifier literal inside `NOT EXISTS` was a complete bypass. Found while implementing #13; fixed with it, zero verdict changes on the dev queries.

### 3.3 Wrong result, different row count (modules B, C, D)

- **Unbound variables** (official-02, official-10, q-054): `?year` in GROUP BY with no `BIND(YEAR(?start) AS ?year)`; a sub-select that projects `?delivery_mode` that nothing binds; `AVG(?days)` over a variable the UNION sub-selects do not export. Each gives one empty-keyed row.
- **Inference on a variable class** (official-07, official-09): `?code a ?concept OPTION (inference ...)` adds every superclass (sphn:SPHNConcept, sphn:Terminology, blank nodes) as extra groups: 121 routes instead of 91.
- **Record link used as a code node** (q-017, q-032): `hasTherapeuticArea` links to a `sphn:TherapeuticArea` record whose category is `hasSpecialtyName`; `?area a ?concept` yields the one class. With `hasSpecialtyName` the generated query reproduces the reference exactly. The card was not retrieved ("medical" matched MedicalDevice/MedicalProcedure), and even when shown it lists no members because the set has 64 values and `build_value_sets.py` keeps at most 15.
- **Missing dimension** (q-006, q-068, official-08): seven identical `COUNT(DISTINCT ?g)` columns instead of a GROUP BY per civil status; a "than other patients" comparison with only the cholera cohort; variants grouped by zygosity instead of their class. In q-006 the guard's retry sentence ("rewrite it so that it only returns results aggregated across all patients") pushed toward the one-row answer.
- **Example shape copied** (q-062, q-025, official-06, q-054): the model reproduces the retrieved example's grouping, filter or sub-select even when the question does not ask for it.
- **q-047 is correct** (wide instead of long); **q-052's reference is wrong** (it lacks the `BilledDiagnosis` restriction the question asks for; the generated query had it) and the generated query exposed a Virtuoso quirk: a sub-select that reuses an outer variable without projecting it is evaluated per outer row.

### 3.4 Wrong result, same row count (modules B, D, eval)

- **Correct answers scored as failures**: q-037 (identical numbers, concept IRIs instead of labels), q-049 ("Continuous" vs "continuous"), q-003 (`ROUND(AVG())` as in the official examples vs `ROUND(10*AVG)/10` as in every dev reference). The comparison in `run_query_eval.signature` is whole-row, case-sensitive, 0.1 rounding.
- **Records counted as patients** (q-011, q-042, q-003 latent): `COUNT(DISTINCT ?g)` under a column named `?total_follow_ups` / `?total_episodes`. The prompt says how to count patients and nothing about records.
- **Aggregates over unbound variables** (q-034, q-064): `AVG(?stay_days)` with no AdministrativeCase pattern; per-patient statistics without the per-patient sub-select (which the model does write in q-035).
- **Code node vs concept** (q-023, q-050): `BIND(IF(?status_code = snomed:385645004, ...))` compares the per-record node with the concept IRI, never true; `VALUES ?concept { icd-10-gm:A00.0 ... } ?c a ?concept` without inference matches only the few year-less code nodes, and the judge's inference check only sees concrete IRIs.
- **Others**: `?date + "P90D"` is NULL in Virtuoso (q-020; `bif:dateadd("day", 90, ?date)` gives the reference's 15); two OPTIONAL blocks under AVG multiply each measure by the other's record count (q-029); a FILTER on a variable that is also averaged restricts the average (q-035); one code per group where the card lists three "do not resuscitate" codes (q-034); `snomed:Country`, a non-numeric SNOMED IRI (official-04).

### 3.5 Empty result (modules C, D)

- **Existing property on the wrong class** (official-03 `SubjectPseudoIdentifier.hasCode`, q-025 `AdministrativeCase.hasStartDateTime`, q-076 `Drug.hasName`, and q-030): the judge checks that a term exists somewhere in the data, not on that class. On the whole dev run the "does not occur in the data" check never fired: the model's real failure mode is existing terms on the wrong class. Swapping to the card's property reproduces the reference (q-025: 767/1233 patients, min 2, max 99).
- **Code-node semantics misapplied**: a value-set entry given `a ?concept` (q-044: `sphn-individual:*` has no `rdf:type` in patient graphs; drop the type triple and the query matches the reference), a Drug record treated as a code node (q-076), one code node joined across two records (official-05: code nodes are never shared, 0 of 925,833), an ICD code on `sphn:Diagnosis` whose code nodes carry only the generic `sphn:Code` type (official-01).
- **Wrong terminology where a class is the handle**: a SNOMED namespace filter on BilledProcedure codes, which are all CHOP (official-06); `icd-10-gm:C18` (colon cancer) for "cancer" where the reference uses the class `sphn:OncologyDiagnosis` (official-01); VitalStatus codes applied to `FollowUp.hasCode` (q-039: the card says `hasResult -> sphn:VitalStatus`, but the VitalStatus card was not among the 6).
- **Card picker**: `SchemaCards.cards_for` matches class-name words by substring (`part in folded`): "average" brings the Age card, "shortest" brings LabTest; "hospital stay", "citizen", "BMI", "active ingredient" bring nothing.

### 3.6 Slow on 100,000 patients and the reorder pass (module B)

- **q-018** (>60 s where the reference takes 3.8 s): an OPTIONAL joins AdverseEvent to every DrugAdministrationEvent row through `hasSubjectPseudoIdentifier ?pid`, re-evaluated per outer row; via `?g` alone it takes 5 ms on dev (150× faster).
- **official-09** (×3.5): inference on a variable class, 5 groups instead of 1.
- **spec-01** (1.42 s vs 0.01 s): the perf optimizer joins the class side before the inference-typed code pattern; the dev optimizer already picks code-first, so dev timings cannot show it (`explain()` through `isql` in the container can).
- **The reorder pass** (`nl2sparql.sparql.order`, off by default) fixed spec-01 (0.02 s) and official-01, and broke q-015 (0.19 → 9.0 s) and q-017 (1.3 → 8.8 s): under `DEFINE sql:select-option "order"` Virtuoso joins in textual order *inside* a `;` chain too, so `?dx a sphn:BilledDiagnosis ; ... ; sphn:hasCode ?dx_code` right after the code pattern is a cross join (every A00 code node × every billed diagnosis of the patient) with the `hasCode` link applied last. Rotating the chain so `sphn:hasCode ?dx_code` comes first gives the organizers' plan (one-row lookup per code node). q-013 "started running" because the DEFINE changes how the duplicate `COUNT(DISTINCT)` is compiled, not because of the order.
- **The anytime `timeout` parameter** (used by `eval/time_on_perf.py` and by curl probes) changes the plan of OPTIONAL + inference queries: on dev the q-013 reference answers in 84 ms without it and runs to the deadline with it, returning HTTP 206 and wrong partial aggregates. UNION, sub-select, MINUS and NOT EXISTS shapes are unaffected.

### Notes on the judge fixes (D)

- **#1 hint texts** (the hint is what the model sees): "Parentheses are not balanced: 14 '(' but 13 ')'. In BIND(IF(..., IF(..., ...))) close every IF and then the BIND. Simpler: BIND(10 * FLOOR(?age / 10) AS ?decade)." / "GROUP BY is written inside the braces of WHERE. Close WHERE first: WHERE { ... } GROUP BY ?x" / "GROUP BY true is not valid. For one overall row leave GROUP BY out." / "Each UNION branch must be a braced group inside WHERE: WHERE { { GRAPH ?g { ... } } UNION { GRAPH ?g { ... } } }." / "SPARQL has no FILTER after an aggregate. Count a subgroup with OPTIONAL { GRAPH ?g { <condition> } BIND(?g AS ?x) } and COUNT(DISTINCT ?x)." / "Window functions (OVER) do not exist in SPARQL. Compute the total in its own subquery." / "'a' is a triple pattern, not an expression: FILTER(?x a <class>) is invalid." / "Class alternatives cannot be written as ?x a <A> | <B>. Write ?x a ?concept . VALUES (?concept ?label) { (<A> "a") (<B> "b") }." Run the diagnosis only when `parse_sparql` returns Invalid; it cannot touch a valid query.
- **#3** walks each `Project` scope: bound = BGP variables, `GRAPH ?g`, `Extend` targets, VALUES keys and the projected variables of nested sub-selects; report variables in the projection, `Group.expr`, `OrderBy` and aggregate inputs that are not bound. Do not report variables used only inside BIND/FILTER expressions (official-04's reference uses an unbound variable inside `IF()` deliberately). rdflib traps: `Variable` is a `str` subclass; a projected GROUP BY key becomes `Extend(?x, __agg_n__)` + `Aggregate_Sample`, which is not a binding.
- **#5** scope rules per SPARQL 1.1 §18.2.1; skip rdflib's `__agg` extends. Virtuoso accepts some re-bindings and rejects others; reject all.
- **#6** flag `YEAR/MONTH/DAY/HOURS/...` whose argument is a triple subject or a datediff target, and `bif:datediff` arguments that are triple subjects; hint with the record's date property from the card (`?death sphn:hasReportDateTime ?reported . FILTER (YEAR(?reported) >= 2015)`).
- **#7** record words in the alias (record, episode, event, stay, case, prescription, diagnos, procedure, test, visit, admission, follow, ...) and no patient word; hint "COUNT(DISTINCT ?g) counts patients, but the column is named ?total_episodes. Count records with COUNT(DISTINCT ?episode)". The "no patient word" variant alone flags official-10's `?births`.
- **#9** for every `?x a sphn:C ; sphn:p ?o` with `p` in the data but not on class `C`, hint "sphn:AdministrativeCase has no sphn:hasStartDateTime in the data. Its properties: hasAdmissionDateTime, hasDischargeDateTime, ..."; when exactly one property shares the suffix, substitute deterministically.
- **#10** exempt class variables constrained by VALUES, and link targets whose instances carry several types (official-08's reference groups by the variant class legitimately).
- **#11 hint texts**: "?route is built from ?code, which is a code node (sphn:hasAdministrationRouteCode): one node per record, not a category. Group by the code's class instead: ?x sphn:hasAdministrationRouteCode ?code . ?code a ?concept . GROUP BY ?concept." / "?intent is a record linked by sphn:hasIntent: a unique IRI per record. Group by the class of its code: ?intent sphn:hasCode ?c . ?c a ?concept." / "?start is an exact timestamp: group by YEAR(?start) or MONTH(?start)."
- **#12** `REQUEST_LEVEL_RULES = {"R1"}` in `guard/decision.py`: `retry_hint` stays None when an R1 violation is present. R1 fired on a first try exactly once on dev (gen-106), so no allowed request is affected. Three tests in `tests/test_guard.py` assert a retry hint for R1 queries and must flip; update the verdict table in `decision.py` and `docs/GUARD.md` §1.

## 5. Harness and reference fixes (eval)

Rescues q-037, q-003, q-047 as `exact_numbers` and q-049 as `exact` (label case); q-050 is not rescuable, its generated query returns 10/13/5 patients against 203/192/191 (the year-less code nodes, fix #19).
- **Keep Virtuoso's error body** (`error.response.text[:300]`) in `execution_error`; today only the HTTP status line survives, which made the error cluster unreadable without re-running.
- **Perf timing**: `eval/time_on_perf.py` must not use the anytime `timeout` parameter for OPTIONAL + inference shapes, or it reports artifacts (q-013 both sides). Time plain runs with a client deadline and restart the container when a query overruns.
- **References**: q-052 lacks `?dx a sphn:BilledDiagnosis` (6,018 prescriptions instead of 4,811); official-03 filters `hasRank Principal` although the question says "any diagnosis rank" (277/256/234 patients by sex, not 102/88/78); official-08 omits the generic `sphn:GeneticVariation` class (58 patients). q-052 is fixed in `eval/query_questions.jsonl` (verified on dev: 15,281 prescriptions, 4,811 for cholera, 405 patients, 31.5%); official-03 is the organizers' own query and stays as given.

## 5b. Second round (17 October night): the 45 dev answers still wrong after the fixes

Four agents diagnosed every dev answer of run 3 that did not give the reference's numbers (same method: executed on dev, judge and guard replayed, context rebuilt, prototypes measured for false alarms on the 64 reference queries). What they found, and what shipped (commit `70e674c`):

- **A hint buys a whole new query, which comes back worse as often as better.** The model's mistakes repeat deterministically (the same first try in 3 of 3 runs), so a shape with exactly one correct form is better repaired than hinted. Shipped: `judge_checks/rewrites_scope.py` (hidden sub-select variables exported, a misnamed COUNT input renamed, a record link typed with a code hopped through `hasCode`, VALUES on a code node typed, a pseudo-identifier "path" in a FILTER dropped, a nested comparison reduced) and `judge_checks/rewrites_aggregation.py` (a per-patient GROUP BY under an aggregate-only SELECT dropped, `COUNT(DISTINCT ?g)` under a record name counting the record, a group key bound only in OPTIONAL filtered, `OPTIONAL { BIND }` lifted, a percentage scale on a statistic undone, a copied subcode regex removed); more syntax repairs (the card placeholder, a bare data property, a scalar subquery in an expression, any `bif:` declaration, a doubled namespace segment). Replayed on run 3: q-020, q-022, q-042, q-050, q-054, q-060, q-064 and q-073 become right with no model call (dev 11 → 19 of 56).

## 6. Data facts learned

- **Code nodes are never shared** between records (0 of 925,833 `hasCode` objects); a code node joined across two records matches nothing.
- **Codes are year-versioned**: `icd-10-gm/2022/A00.1`, `chop/2016/00.03`; `?code a ?concept` + `GROUP BY ?concept` without inference splits one code across years; a few year-less nodes exist (`icd-10-gm/A00`: 5 patients), so a query without inference returns a handful of rows instead of none.
- **17 classes carry only the generic `sphn:Code`** (Diagnosis, NursingDiagnosis, OncologySurgery, MedicalProcedure, DrugArticle, AdverseEvent, LabResult, ProblemCondition, Gene, ...): any ICD/CHOP/SNOMED pattern on them is empty by construction. BilledDiagnosis and OncologyDiagnosis are ICD-10-GM, BilledProcedure is CHOP, 38 classes are SNOMED.
- **Value-set entries** (`sphn-individual:*`) have no `rdf:type` inside patient graphs; they are categories, group by the entry itself.
- **Virtuoso silences**: `?date + "P90D"` is NULL, `?date + 90` adds seconds, `BIND ... AS ?alreadyBound` is sometimes ignored, `bif:datediff` on NULL raises DT001, a BIND inside OPTIONAL cannot see outer bindings, a sub-select that reuses an outer variable without projecting it is evaluated per outer row.
- **Mock-data quirks** that make some official questions degenerate: gestational ages are 10–9,975 "days"; `DrugAdministrationEvent.hasDuration` carries random units (Ms, Hz, ...); `DeathDate.hasYear` values are garbage (`-9979`); cancer ICD codes exist for 2+2 patients only (cancer is only answerable through `sphn:OncologyDiagnosis`, 78 patients); no prescription shares a route with an administration of the same case (official-05's first category is empty on dev); only 31 of 4,437 imaging procedures start inside their own stay.
- Dev has exactly one AdministrativeCase per patient, which hides "records vs patients" mistakes on stays.
- **Virtuoso drops GROUP BY groups when a variable predicate is joined with `?o a ?type`** (`?s a <C> ; ?p ?o . ?o a ?type ... GROUP BY ?p ?type`): on dev, Assay.hasSample and Interpretation.hasOutput came back with no type at all and nine link frequency orders were wrong. Profile one fixed property at a time (`scripts/profile_data.py`, `scripts/build_value_sets.py`).
- `sphn:DeathDate` and `sphn:BirthDate` carry the date as literal parts (hasYear, hasMonth, hasDay); the dateTime of a death is `sphn:Death.hasReportDateTime`. `YEAR()` on a record IRI or on a `bif:datediff` number raises DT001 in Virtuoso.
